## 4. Adopted game-domain principles

Unless a later cross-domain review rejects them, the synthesis adopts these compatible producer principles.

### 4.1 Sandbox and progression

- optimize for meaningful trajectories and interacting possibilities, not catalog counts;
- allow soft specialization/hybridization without rigid classes by default;
- retain one shared world while giving foundational needs multiple routes where practical;
- progression should increase capabilities, choices, knowledge, access, leverage, scale, and world influence, not only numbers;
- discovery should reveal actionable depth progressively rather than expose the whole database or hide important rules arbitrarily;
- important irreversible choices require signaling, sufficient branch content, and explicit recovery/alternative analysis.

### 4.2 Economy and automation

- use a multi-dimensional source/sink/transformation model rather than one money-per-time ladder;
- general currency may support exchange but should not automatically bypass all knowledge/relationship/progression value;
- automation exchanges recurring labor/attention for setup constraints and leverage;
- stronger automation should create higher-order decisions rather than passive waiting;
- manual/direct play may remain lower-throughput while still supporting meaningful goals;
- late game needs several optional ambition/sink families rather than only price inflation.

### 4.3 World, social, narrative, and content

- gameplay/continuity-relevant truth is explicit structured state rather than living only in prose/scripts;
- objective facts, character knowledge/beliefs, player discovery, secrets, chronology, and branch facts remain distinguishable;
- quests expose typed preconditions/objectives/effects/branches/failure semantics and structural solvability evidence;
- NPC schedules/goals react through explicit world-state rules and are checked for conflicts/reachability;
- generated/authored prose/media are candidates bound to canonical briefs/provenance and cannot silently invent canonical truth;
- structural consistency does not replace subjective writing/character/world-quality review.

### 4.4 Runtime and persistence

- canonical gameplay meaning is engine-independent logical state; presentation/editor objects are adapters, not sole authority;
- stable IDs, versioned schemas, validated references, commands/events/queries, migrations, and deterministic content packaging are foundational seams;
- gameplay evidence uses declared deterministic boundaries, named RNG/time/order rules, save/replay state, and real/shared gameplay rules;
- player-surface evidence and simulation evidence remain separate but linked.

### 4.5 Experience/accessibility/media

- broad gameplay requires progressive legibility/discovery rather than giant-menu exposure;
- gameplay normally consumes semantic actions, not hard-coded device keys/buttons;
- accessibility is architectural and task-evidence driven, not post-hoc toggle presence;
- current standards/platform obligations require authoritative research before readiness/release gates;
- media candidates bind stable identity, brief, provenance, technical checks, controlled captures, and structured subjective review;
- final style remains an evidence-driven later selection.

### 4.6 Evaluation

- evidence is claim-specific; no universal green status or fun score;
- semantic gameplay transition/path coverage matters more than code/object-touch counts for game possibility claims;
- scenarios/golden/protected cases bind exact build/content/state/actions/seeds/evaluator versions and use real/shared gameplay rules;
- synthetic policies are versioned evaluation models, not human preference models;
- exploit/search, long simulation, structured subjective panels, protected probes, and evaluator drift tests complement deterministic checks;
- no evaluator family/tool is assumed reliable before benchmark evidence.

## 5. Review finding dispositions

### GE-M01 — ACCEPTED_AND_CORRECTED: shared progression/gate authority

**Problem:** GDF/EPA/WSN each discuss gates/optional routes but no shared typed object prevents social, narrative, economy, or automation prerequisites from becoming a hidden canonical playthrough.

**Decision:** define `ProgressionGateContract`.

```yaml
ProgressionGateContract:
  version: 1
  gate_id: <stable>
  gate_class: FOUNDATIONAL | SPECIALIZATION | OPTIONAL | BRANCH_EXCLUSIVE
  blocks_or_unlocks: []
  requirements: []
  routes:
    - route_id: <stable>
      route_kind: DIRECT_SYSTEM | TRADE | SERVICE | RELATIONSHIP | QUEST | KNOWLEDGE | SUBSTITUTE | OTHER
      prerequisite_refs: []
      lifestyle_impacts: []
  visibility_or_discovery: []
  miss_failure_recovery: <rule>
  branch_scope: <optional>
  evidence_requirements: []
  exception_rationale: null
```

Rules:

1. A foundational gate must expose enough route/substitution evidence to demonstrate intended sandbox viability.
2. A single-route foundational gate is allowed only as an explicit reviewed common-foundation decision, never by accident.
3. Social/narrative/automation-specific gates cannot silently become foundational by being required downstream; classification must be updated/reviewed.
4. Branch-exclusive gates state which goals/content become unavailable and bind `BranchImpactEvidence`.
5. Evaluation compiles gate/route state into the semantic graph and reachability scenarios.

This corrects GE-M01 without requiring total self-sufficiency or equal progression across lifestyles.

### GE-M02 — ACCEPTED_AND_CORRECTED: one game-time contract

**Problem:** simulation, day/session planning, schedules, timed quests, waiting, automation, menus/dialogue, and timing/accessibility assists can otherwise advance time differently.

**Decision:** define `GameTimePolicy` as canonical game-design input.

```yaml
GameTimePolicy:
  version: <ref>
  canonical_time_domains:
    simulation_time: <definition>
    calendar_time: <definition or mapping>
  contexts:
    gameplay_world: <ADVANCE | FREEZE | SCALE + rule>
    menu_inventory: <rule>
    dialogue_cutscene: <rule>
    pause: <rule>
    loading_transition: <rule>
    automation_headless: <rule>
  timed_window_types:
    - type: <id>
      clock_domain: SIMULATION | CALENDAR | REAL_EXTERNAL
      pause_scale_semantics: <rule>
  accessibility_timing_alternatives: []
  wall_time_inputs: []
  evidence_scenarios: []
```

Rules:

- gameplay rules never read ambient wall clock implicitly;
- each timed objective/event/schedule names the clock domain/pause semantics;
- accessibility pause/slow/timing assists declare whether they alter canonical challenge/economy windows rather than relying on UI behavior accidentally;
- headless/accelerated simulation and player execution use the same policy version;
- the exact day/season/tick durations remain later empirical decisions.

### GE-M05 — ACCEPTED_AND_CORRECTED: runtime generative authority boundary

**Problem:** runtime LLM/generative NPC/dialogue/content can either be presentation or affect canonical state; those cases need different persistence/replay authority.

**Decision:** define `GenerativeRuntimeBoundary`.

```yaml
GenerativeRuntimeBoundary:
  generation_id_or_class: <stable>
  authority_class: BUILD_TIME_CANDIDATE | RUNTIME_PRESENTATION_ONLY | RUNTIME_CANONICAL_EFFECT
  model_tool_config_ref: <versioned if applicable>
  input_context_refs: []
  allowed_fact_invention_scope: <bounded>
  output_schema: <ref>
  failure_fallback: <rule>
  provenance_policy_ref: <ref>
  canonical_effect_contract: null | <command/effect refs>
  persistence_rule: <rule>
  replay_rule: <rule>
  nondeterminism_declaration: []
  evidence_requirements: []
```

Rules:

1. Build-time generated content remains a candidate until normal validation/review.
2. Runtime presentation-only generation cannot mutate canonical facts, gates, rewards, relationships, or world state.
3. Runtime canonical-effect generation cannot mutate state directly. A validated accepted command/effect is the canonical transition.
4. The accepted output/effect and enough provenance to interpret/replay it are persisted. Replay normally reuses the accepted canonical result rather than calling an external model again.
5. Any intentional nondeterministic canonical boundary is explicit, versioned, and tested; verifier evidence cannot claim deterministic replay across an undeclared external generation call.
6. Model/service outage produces a declared fallback/inconclusive path, not arbitrary canon.

## 7. Coherent game/experience model

### 7.1 One world, many trajectories

Everfield’s target is a shared persistent world in which players can emphasize different combinations of production, exploration, social life, quests, commerce, crafting, automation, infrastructure, collection, combat/risk, and later-selected systems.

The design does not promise full self-sufficiency. It promises that shared foundational requirements are explicit and reviewed, specialization-specific gates remain scoped, and multiple routes/trade/services/substitutions preserve meaningful choice where intended.

### 7.2 Multi-horizon play

The game should create decisions at:

- moment/action horizon;
- day/session planning horizon;
- medium calendar/season/event horizon where selected;
- project horizon;
- long specialization/world/infrastructure/social horizon.

`GameTimePolicy` determines how those horizons interact operationally. No exact day/season duration is selected here.

### 7.3 Progression in agency

Major progression should increasingly provide:

- new verbs/capabilities;
- new locations/access;
- knowledge/discovery;
- relationships/social/world influence;
- tools/efficiency/leverage;
- infrastructure/automation/logistics;
- customization/expression/mastery;
- recovery/risk management;
- new project/late-game ambition classes.

Pure numerical growth may exist but should not define the whole progression chain.

### 7.4 Chore, ritual, and automation

Repeated activity is evaluated by whether it still creates learning, mastery, satisfying ritual, planning, or meaningful tradeoffs. Low-decision maintenance burden should acquire optional relief as scale/mastery rises.

Automation may exchange labor/attention for capital, materials, knowledge, space, maintenance, logistics, energy, reliability, relationships, or opportunity cost. It should create decisions at a higher abstraction level after relieving lower-level burden.

`LifestyleViabilityEvidence` prevents this fantasy from silently turning into mandatory industrialization.

### 7.5 Economy and value

The economy includes money/resources but also time, attention, access, knowledge, relationships, risk, capacity, world state, and opportunity. Not all are fungible currencies.

Every important resource/capability should eventually expose its sources, sinks/uses, gates, substitutes, lifecycle, and exploit/dominance evidence. General currency is useful but does not automatically bypass every progression domain.

### 7.6 Narrative and social participation

NPC/social/narrative content is a first-class source of goals, information, access, consequences, services, relationships, and world identity. It does not automatically become required common progression: its gates use `ProgressionGateContract`.

Objective truth, character knowledge/beliefs, player discovery, secrets, chronology, and branches remain explicit. Generated text cannot silently define canon.

### 7.7 Discovery and legibility

The full possibility graph should not be dumped into one UI. Important actions/gates/status/recovery are legible; optional depth appears through environmental, social, quest, interface, experimentation, progression, and collection/map/log channels appropriate to its importance.

Hidden optional content may remain mysterious. Foundational progression cannot depend on unknowable arbitrary actions.

### 7.8 Accessibility

Semantic input, layout/text expansion, redundant critical information channels, timing/motion/audio alternatives, focus/navigation, challenge assistance hooks, pause/save/session resilience, and real-task evidence remain architectural obligations.

`IR-BLOCKER-ACCESSIBILITY-CURRENT` makes clear that these foundations are not a substitute for current authoritative standards/platform research.

### 7.9 Media and originality

Final style is selected later through comparable gameplay-constrained candidates, technical/readability/accessibility/production evidence, provenance, and structured subjective review.

`OriginalityReferenceUseRecord` ensures reference inspiration/provenance cannot be confused with permission to reproduce source expression.

### 7.10 Evaluation

The game-domain evaluator portfolio uses:

- deterministic tests/invariants/replay;
- real/shared-kernel scenarios;
- semantic graph/coverage;
- progression/quest state search;
- accelerated economy/world/NPC simulation;
- persona distributions;
- exploit/fuzz/adversarial search;
- controlled player-surface visual/audio/input evidence;
- structured subjective panels;
- selected protected scenarios/probes;
- evaluator version/drift and trust evidence.

No single result replaces the others for claims outside its scope.

## 12. Failure modes and defenses

### Hidden canonical playthrough

**Failure:** one economy/social/quest/automation route becomes foundational by composition.  
**Defense:** `ProgressionGateContract`, route evidence, `LifestyleViabilityEvidence`, semantic reachability.

### Time-policy divergence

**Failure:** headless simulation, menus/dialogue, timed quests, NPC schedules, or accessibility assists advance time differently.  
**Defense:** one versioned `GameTimePolicy` bound to scenarios/saves/rules.

### Coverage theater

**Failure:** test suite covers objects/tags but not intended paths/substitutions.  
**Defense:** `GameSemanticGraph` version mapping and path/trajectory coverage.

### Industrialization mandate

**Failure:** manual/cozy/direct play exists only cosmetically.  
**Defense:** stage/goal `LifestyleViabilityEvidence` and explicit automation dependency.

### Runtime AI becomes hidden canon

**Failure:** external/generative output changes quest/relationship/world state but cannot replay/persist.  
**Defense:** `GenerativeRuntimeBoundary` and typed canonical command/effect persistence.

### Accessibility polish deferral

**Failure:** architecture declared ready while applicable obligations remain unknown.  
**Defense:** explicit readiness blocker tied to current authoritative research.

### Reference-expression drift

**Failure:** provenance-complete generated content too closely imitates a reference.  
**Defense:** `OriginalityReferenceUseRecord`, similarity/red-team/quarantine and authoritative research.

### Judge panel monoculture

**Failure:** repeated correlated evaluator calls create false consensus.  
**Defense:** `SubjectivePanelTrust`, factory trust mapping, disagreement/drift/protected evidence.

### Cross-system edge inflation

**Failure:** every item/system is linked everywhere to increase “depth.”  
**Defense:** semantic-value refs, coupling/fan-out/evaluation-cost diagnostics.

### Golden-path ossification

**Failure:** regression suite becomes the preferred game route.  
**Defense:** multiple trajectory intersections, semantic gaps, protected/rotating/adversarial scenarios.
