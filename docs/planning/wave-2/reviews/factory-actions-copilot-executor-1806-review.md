### FCE-1809-M01 — unpinned executable supply chain with later billable GITHUB_TOKEN (MAJOR)

The source's `Install latest Copilot CLI for GITHUB_TOKEN support` step executes **`npm install --global @github/copilot`**, selecting whatever npm package and transitive code is current for each future workflow run. Unlike the separately pinned checkout action, neither package version nor resolved dependency integrity is fixed, and npm install may execute package lifecycle code. The next step runs the newly downloaded `copilot` executable with an explicitly exported **`GITHUB_TOKEN`** whose actual hosted permissions include `CopilotRequests: write`. Thus an upstream compromised/replaced package or dependency can change model behavior, forge the fixed sentinel or exfiltrate the later token, with billable permission, despite a byte-identical reviewed Git source workflow. The observed successful job proves only what npm served at that moment. This is a post-review executable trust-boundary breach and **must be hardened before publication**.

Corrective route: deterministically pin a previously inspected trusted CLI distribution and its transitive executable dependency tree (e.g. verified integrity/lock or immutable signed release digest, with safe lifecycle-script handling), and show exact reproducible hosted behavior and token exposure analysis. Merely naming an npm major tag or `latest`, or trusting a successful one-off run, does not fix immutable provenance. GitHub's secure-use reference expressly recommends immutable pinning for executable Actions dependencies; apply analogous integrity control to downloaded npm code. Source owner already called this unpinned install a known review gate, not an accepted waiver.

### FCE-1809-M02 — unreviewed same-repository PR can execute PR-controlled billable workflow (MAJOR)

The only privileged job has `on: pull_request` (with watched path **including the workflow file itself**), no protected-main-only gate, and the job condition checks only that the PR **head repository name** is `vokerg/everfield`. A collaborator able to push a branch and open a same-repo PR can edit the workflow file, thereby causing PR-selected GitHub Actions workflow instructions—not yet reviewed or squash-integrated into main—to execute with `copilot-requests: write`. The predicate blocks forks, but **does not require immutable owner-reviewed trusted workflow code** or an explicit approved expense decision. Its `workflow_dispatch` manual-main branch is a safer route, but is bundled with the automated PR event.

This is not hypothetical scheduling inference: run #39021587655 actually executed `everfield-frontier-copilot-probe.yml` while the file existed **only in unmerged PR #1808** (new/added vs unchanged main). GitHub's security documentation confirms `pull_request` workflows run PR merge-commit workflow code; same-repo pull requests retain write-capable job tokens under normal repo permission policy, while forks usually get read-only tokens. A SHA-pinned checkout ref only pins the code fetched *after* GitHub already selected the PR workflow; it does not pin the workflow's own command steps. A contributor could replace the fixed prompt, spend repeated billable requests, or use the token from an unreviewed runner. Current trusted authored run used a fixed prompt, but the trigger is still a latent authority/cost gap.

Required fix before integrated reusable probe: keep billable model jobs **off unreviewed PR workflow events**, for example a main-only owner-approved manual dispatch gated to an immutable main workflow. Untrusted PR validation can use a separate zero-Copilot-permission static job. If source CI must still run before publication, clearly separate safe PR tests from a privileged step that cannot run on PRs. Explicit cost/approval and bounded rate/quota policies are required before moving toward a dispatcher. Do not attempt a test by deliberately exfiltrating a token or consuming model quota.

### FCE-1809-m01 — output sentinel check accepts non-exact responses (MINOR, correction required)

The script intends to accept exactly **one plain-text line**, but its condition is `printf '%s\n' "$response" | grep -Fxq 'EVERFIELD_COPILOT_ACTIONS_PROBE_OK'`. `grep -Fxq` checks for *any* whole line, not exact equality of the full response. The real local Bash reproduction:

```bash
response="$(printf 'unexpected extra line\nEVERFIELD_COPILOT_ACTIONS_PROBE_OK\n')"
printf '%s\n' "$response" | grep -Fxq 'EVERFIELD_COPILOT_ACTIONS_PROBE_OK'
echo "$?"  # 0; falsely accepted as exact output
```

The hosted final response was actually a single sentinel line and remains credible evidence of model reachability, but a later noisy/multi-line reply could be marked as meeting the stricter asserted invariant. Compare the *entire* trimmed response using Bash string equality, reject extra leading/trailing lines, and preserve error logs without leaking secrets. This is a bounded evidence-integrity correction, not evidence that the first hosted run was forged.
